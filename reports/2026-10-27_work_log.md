## 1. Began requirement R1: gesture-recognition accuracy

R1 requires at least 95% recognition accuracy. The defined test uses 30 trials
per gesture and at least two operators. A gesture passes with at least 29
correct detections out of 30 for each operator.

The first test covers the two currently implemented vertical gestures:

- Raise the wand while holding IO1: `takeoff`
- Lower the wand while holding IO1: `land`

This is intentionally a dry test. The drone controller and wand coordinator
are not used, so the test cannot command the `cf1` drone.

## 2. Added an interactive R1 trial logger

Created:

- `src/cf_control/cf_control/gesture_trial_logger.py`

The logger:

- Subscribes to `/wand/detected_gesture`.
- Alternates between 30 takeoff trials and 30 landing trials.
- Prompts the operator before opening each response window.
- Records the intended gesture, detected gesture, correctness, response time,
  operator identifier, trial number, and timestamp.
- Saves partial results if the session is interrupted.
- Calculates the final correct/total count for each gesture.
- Reports a pass only when all 30 trials were completed and at least 29 were
  correct.

Results are written locally under:

```text
output/test_results/
```

The `output/` directory is ignored by Git so experimental data is not
accidentally mixed with source-code commits.

## 7. Restored Crazyradio access in Ubuntu 24.04

The Crazyradio was already attached to WSL as Windows USBIP BUSID `2-2`, but
its current Linux device path had changed to:

```text
/dev/bus/usb/001/002
```

The device permissions allowed root to write but allowed ordinary users to
read only. Temporary read/write access was applied to the current device node.
A non-actuating cflib scan then completed without an access-denied exception.
The scan returned no radio targets, which indicates that no powered Crazyflie
was detected on the scanned channels at that moment; it does not indicate a
USB permission failure.

Later, USBIP re-enumerated the dongle as `/dev/bus/usb/001/004`, which reset
the temporary permission and caused another access-denied error. Access was
applied only to that exact device. Verification showed `crw-rw-rw-`, and
cflib again completed a scan without a permission exception. No persistent
world-writable udev rule was installed.

## 8. Cleared duplicate wand nodes and Fast DDS lock failure

Four duplicate `wand_button_node` processes were found. They caused a Fast DDS
shared-memory port error and were simultaneously blocked inside the USB kernel
driver. Because the processes were in an uninterruptible wait, normal interrupt
and termination signals could not stop them.

WSL was shut down and restarted to clear the stale kernel and DDS state. The
Crazyradio was then reattached through USBIP as BUSID `2-2`, appeared in Ubuntu
as `/dev/bus/usb/001/002`, and received temporary access permission. A fresh
cflib scan completed without USB or Fast DDS errors. The scan still returned no
radio target, so the next step is to power on `cf2` and run exactly one button
node process.

After the WSL restart, the Crazyradio device appeared before its final udev
permissions settled. It was later recreated at the same path with mode
`crw-rw-r--`, producing one more access-denied error. With no wand process
running, temporary access was reapplied and verified as `crw-rw-rw-`. No
additional scan was run afterward so that the next USB user would be the one
required R1 wand node.

Windows subsequently reassigned the Crazyradio from USBIP BUSID `2-2` to
BUSID `2-1` and left it shared but unattached. This caused a dongle-not-found
error in Ubuntu. BUSID `2-1` was attached to Ubuntu 24.04, where it appeared as
`/dev/bus/usb/001/003`; temporary access was applied and verified.

### Vicon update-rate observation

A live `ros2 topic hz /vicon/cf1/pose` measurement reported approximately
82–83 Hz, with a maximum inter-message interval of about 1.12 seconds. This is
not sufficiently continuous for the controller's approximately 0.25-second
pose timeout. The long interruption can return the aircraft state to
`DISARMED` and makes another flight attempt unsafe until the pose stream is
stable. The next diagnostic is a short-window rate check while watching for
occlusion in Tracker.

The follow-up 20-sample-window measurement confirmed that individual pose
messages are normally separated by roughly 0.006–0.053 seconds, but another
1.101-second dropout occurred. The displayed short-window rate varied from
about 15 Hz to 121 Hz. Because the dropout exceeds the pose timeout, the Vicon
stream did not pass the live-flight continuity check.

A 100-packet network test to Tracker (`10.86.153.14`) returned 100/100
packets with 0% loss. Round-trip latency was 5.321 ms minimum, 15.847 ms
average, and 85.105 ms maximum. This does not explain the observed 1.1-second
pose gap. Code inspection confirmed that the Vicon bridge intentionally skips
publishing a subject frame whenever the SDK reports its translation or
rotation as occluded. The next physical check is therefore continuous `cf1`
rigid-body visibility and marker reconstruction quality inside Tracker.
